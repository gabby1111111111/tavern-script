# 杠杠の生图机 Agent Guide

本文件只约束 `src/杠杠の生图机/`。它是一个独立的 Tavern Helper 后台脚本，不得把其他 `src` 脚本、旧版 JSON 或
`src/st测试` 的实验协议整体迁入。

## 先理解产品

这个项目不是图片档案馆，而是聊天正文旁边可随时插拔的轻量视觉增强：正文永远优先，图片在后台异步生成；偶发失败可以接受，不能因为等图、重试或恢复历史图片拖住聊天。

- 图片、图片列表和 placement 只保存在本次浏览器页面生命周期的 JavaScript 内存；只有用户明确点击时才保存到角色图库。
- 不把图片、Base64、图片地址或任务状态写进正文、聊天变量、消息变量、`localStorage`、IndexedDB 或 `image2store://`。
- 默认每个图片任务只请求一次；失败即止，不增加隐式重试、长循环、后台补跑或持久队列。
- 正文插图与礼物异步共用同一生成流水线；一次请求可以返回多张横向候选，重绘可以形成纵向版本。任务数、候选数等可变产品限制以目标版本代码和 README 为准，不在 AGENTS 中写死。
- 有人物时，“是不是这个角色”比画面单纯漂亮更重要；脸和角色识别度是硬约束，背景、服装和构图可以适度妥协。
- 先满足项目作者的真实使用方式，再讨论面向所有用户的泛化设计。

## 与 Gabby 协作

- 使用中文，先讲用户可感知的结论，再补必要的技术原因。
- 她不需要认识每个函数和变量，但必须能看懂“事件 → 核心函数 → 状态/API/DOM
  → 审计证据”的线路。解释故障时必须指出该走哪条线路排查。
- 语音输入可能重复或有同音字；结合上下文理解意图，不纠缠口误。
- 功能代码默认交给子 Agent 开发。主 Agent 先与 Gabby 确认方案，再写成包含目标、允许路径、禁止路径、文件所有权和 `Step N`
  验收的执行简报；子 Agent 在边界内实现，主 Agent 不与其并发写同一文件，并负责独立审查实际 diff、复跑验证和最终说明。只读调查、方案讨论和文档整理可以由主 Agent 直接完成。
- 如果环境没有可用子 Agent，或任务无法安全拆给子 Agent，主 Agent 必须先向 Gabby 说明原因；不能在未说明的情况下把“默认子 Agent 开发”静默改成主 Agent 直接写功能代码。
- 讨论方案阶段不得擅自开始改代码。只有 Gabby 明确表示方案已经确认并要求“开始开发”或“让子 Agent 开发”后，才能进入实现阶段。
- 重大版本更新或产品大方向改变必须增加讨论轮次，不能把 Gabby 在探索想法时说出的第一版方案直接当成最终开发指令。主 Agent 应主动询问并帮助核对用户体验、默认行为、数据流、失败与降级、请求次数与成本、存储边界、Swipe/删楼等真实使用场景、验收标准和明确非目标；给出可比较的方案与代价，直到关键选择由 Gabby 确认后再委派开发。
- “重大版本或大方向”至少包括：版本主功能、模块重组、正文 AI 输入变化、参考图协议、自动触发与请求次数、持久化语义、公开设置结构、聊天正文修改，以及会改变既有工作流的交互。即使技术上可以直接实现，也必须先问清楚。
- 不用大段测试术语淹没她。把结论分成：Codex 已验、真实运行时待验、只需她感受的人工验收。
- 如果礼物异步、连续剧情图、参考图来源或存储语义尚未想清楚，先讨论体验，不替她做会改变产品方向的决定。
- 任何会增加持久化、请求次数、重试、自动触发、正文修改或外部发送内容的方案，都要先说清收益和代价并取得确认。
- 截至 2026-09-05，产品只有 Gabby 一位实际用户；除非她在后续任务中明确改变范围，不为假设中的旧用户、迁移路径或兼容场景增加实现负担。

## 版本与路线边界

- [docs/ROADMAP.md](docs/ROADMAP.md)
  是未来版本规划与带日期阶段说明的唯一入口；路线中的候选功能不是实现授权，也不能写成已经交付。
- 截至 2026-09-05，工作范围仍以已发布的 `杠杠の生图机-v0.3.0`
  为产品查错基线，只处理真实使用中发现的小 bug。Gabby 明确宣布开始 v0.4 前，不得自行实现
  `{{xx_pic}}`、上一剧情图引用或自由参考图系统。
- “v0.3 基线”指生图机专属发布 tag，不代表执行任务时 live checkout 的 HEAD。每次开工必须重新记录
  `git branch --show-current`、`git rev-parse HEAD`、目标 tag commit、与 `origin/main`
  的 ahead/behind 以及目标目录 dirty 状态；以当次命令结果为准，不照抄 ROADMAP 中的历史快照。
- 已知 live checkout 可能让旧 Git 指针与较新的磁盘内容并存。未先完成 `src/杠杠の生图机`、对应 `tests/story-image-*`
  和目标 dist 的精确范围审计时，不得 pull、切分支、合并、rebase、reset、提交或发布。
- 文档职责必须分开：README 只写目标发布版本已经可用的功能，CHANGELOG 只写已经完成或明确进入 `[Unreleased]`
  的用户变化，ROADMAP 写尚未开发的版本方案，AGENTS 只保留执行边界和长期开发规则。

## 代码与状态边界

- 任务和正文图片身份必须覆盖 `chatId + messageId + swipeId + imageIndex + variantIndex + revisionIndex`
  对应的层级；旧 generation、其他聊天、失效 swipe、横向候选、纵向版本和失效参考图的迟到结果不得覆盖仍有效状态。
- `runtime.ts` 只负责编排事件、门控、生命周期、DOM 放置和审计；解析、缓存、API 请求与渲染细节留在各自模块。
- 公开设置必须有可理解的界面；内部端口或测试基础设施不等于已经交付的用户功能。
- 设置抽屉标题必须显示完整版本号，并与目标发布的脚本专属 Git tag 和 CHANGELOG 版本一致。
- API 配置、提示词和 Key 可以按现状保存在 Tavern Helper 脚本变量；必须明确 Key 为明文，不得把它误称为安全密钥库。
- 审计对象固定为 `window.__storyImageAudit`，日志前缀固定为 `<杠杠の生图机>`。
- 审计、正文、日志和报错不得包含 API Key、Base64、图片地址、完整响应、完整聊天记录或大段提示词。
- 优先使用仓库 `@types` 已声明的 Tavern Helper 高层接口；不得凭记忆调用私有 SillyTavern
  API，也不得用 STScript 绕开已有接口。

## 允许失败的语义

- 图片请求失败：留下最小失败状态，正文继续。
- 礼物异步展现条件不足或请求失败：记录 `skipped` 或 `failed`，不排队、不补跑。
- 礼物已经生成成功但到达通知失败：只允许影响通知状态，不能把礼物任务改判为失败。
- generation、聊天、消息或脚本生命周期变化：取消或丢弃过期结果，并释放页面内资源。
- 生图开关关闭：不得扫描、清理或回写正文，也不得发起图片任务；inline/gift 由统一展现设置选择。

## 阅读与排障顺序

先读 [README.md](README.md) 理解公开行为，再读 [docs/ROADMAP.md](docs/ROADMAP.md)
确认带日期的阶段说明与 Git 锚点，最后读 [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md)
找到对应线路；只有定位到线路后才深入具体函数。不要从全仓库盲搜开始，也不要把某个测试函数当成生产入口。

## 验收与发布

- Codex 验收：目标目录 ESLint、目标测试、生产构建、diff 与敏感信息检查。
- 运行时验收：真实 SillyTavern 中核对
  `window.__storyImageAudit`、console、事件时序、User/角色头像参考、候选与版本交互，以及实际使用的图片 API 模式。
- 人工验收：只留视觉观感、角色像不像、交互是否顺手和实际聊天节奏。
- 静态构建成功不能冒充真实运行时或真实 API 已通过；暂缓的人工验收必须明确列为待验。
- 同一文件同一时刻只能有一个写入者。未经明确授权不得修改根配置、其他脚本、依赖或锁文件，也不得 commit、pull、merge、rebase、push、tag 或发布。
- 发布时严格按目标脚本目录及其测试限定 diff；不得使用 `git add .` 或 `git add -A`。
